DEVOPS PROJECT 5: MULTI-CLOUD
SERVICE MESH IMPLEMENTATION
Project Objective

The objective of this project is to build a secure and observable communication environment
between microservices deployed across multiple Kubernetes clusters using Istio Service
Mesh.

Students will configure Kubernetes clusters, establish cross-cluster communication, deploy
sample microservices, implement mutual TLS (mTLS), configure traffic routing, and monitor
service communication.\

Technology Stack

      Cloud Platforms: AWS (EKS) and Google Cloud (GKE)
      Container Orchestration: Kubernetes
      Service Mesh: Istio
      Proxy: Envoy
      Monitoring: Prometheus and Grafana
      Service Mesh Visualization: Kiali
      Distributed Tracing: Jaeger
      Configuration: YAML
      Command Line: Linux Terminal / Cloud Shell

ACTIVITY 1: MULTI-CLOUD
KUBERNETES CLUSTER SETUP AND
ISTIO SERVICE MESH DEPLOYMENT
Objective

In this activity, students will create two Kubernetes clusters using AWS EKS and Google
Cloud GKE, install Istio Service Mesh, configure communication between the clusters, and
deploy a sample microservices application.

By completing this activity, students will establish the infrastructure and service mesh
foundation required for the complete project.

Tools Required

   1.   AWS Account
   2.   Google Cloud Account
   3.   AWS CLI
   4.   Google Cloud CLI (gcloud)
   5.   kubectl
   6.   eksctl
   7.   Istio CLI (istioctl)
   8.   Git

Important: Creating EKS and GKE clusters may incur cloud charges. Students should use
approved educational cloud accounts, check current pricing and quotas, and delete their
resources after completing the project.

Students can use:

       Google Cloud Shell for Google Cloud operations.
       A Linux machine with the required cloud CLIs installed.

For the easiest workflow, use one Linux terminal with AWS CLI, Google Cloud CLI, kubectl
and eksctl configured.

Execute the following commands:

aws --version
gcloud --version
kubectl version --client

These commands verify whether the required tools are installed.

Expected Result: The terminal should display the installed versions of the tools.

Step 3: Configure AWS Access

Execute:

Enter the following information when prompted:

       AWS Access Key ID
       AWS Secret Access Key
       Default Region: us-east-1
       Default Output Format: json

Verify the configuration:

aws sts get-caller-identity

Step 4: Configure Google Cloud Access

Execute:

Follow the instructions to:

Expected Result: The terminal should display the active Google Cloud project and

PART B: Create the AWS Kubernetes Cluster
Step 5: Create an EKS Cluster
Execute:

eksctl create cluster \
--name eks-mesh \
--region us-east-1 \
--nodes 2 \
--node-type t3.medium

Explanation:

       eksctl create cluster: Creates a Kubernetes cluster.
       --name eks-mesh: Assigns the cluster name.
       --region us-east-1: Selects the AWS region.
       --nodes 2: Creates two worker nodes.
       --node-type t3.medium: Specifies the worker node type.

Wait until the cluster creation process is completed.

Step 6: Verify the AWS Cluster

Execute:

kubectl get nodes

Then:

kubectl get pods -A

Expected Result:

       The Kubernetes nodes should appear in the output.
       The nodes should eventually show Ready.
       System pods should be running.

Save a screenshot of the node information.

PART C: Create the Google Cloud Kubernetes Cluster
Step 7: Create a GKE Cluster

Execute:

gcloud container clusters create gke-mesh \
--zone us-central1-a \
--num-nodes 2

This command creates a Google Kubernetes Engine cluster with two worker nodes.

Wait until the cluster creation process is completed.

Step 8: Connect kubectl to the GKE Cluster
Execute:

gcloud container clusters get-credentials gke-mesh \
--zone us-central1-a

This command updates the Kubernetes configuration so that kubectl can communicate with
the GKE cluster.

Step 9: Verify Both Clusters

Execute:

kubectl config get-contexts

You should see the available Kubernetes contexts.

Check the AWS cluster:

kubectl get nodes --context <EKS_CONTEXT>

Check the Google Cloud cluster:

kubectl get nodes --context <GKE_CONTEXT>

Replace the context names with the actual names displayed by your terminal.

Expected Result: Both clusters should be accessible, and their worker nodes should show
Ready.


PART D: Install Istio Service Mesh
Step 10: Download Istio

Execute:

curl -L https://istio.io/downloadIstio | sh -

Move into the downloaded Istio directory:

cd istio-*

Add Istio to the system PATH:

export PATH=$PWD/bin:$PATH

Verify the installation:

istioctl version

Expected Result: The terminal should display the installed Istio CLI version.
Step 11: Install Istio in the Primary Cluster

For this activity, use the AWS EKS cluster as the primary cluster and GKE as the remote
cluster.

Set your cluster context variables using the actual context names:

export CTX_CLUSTER1=<EKS_CONTEXT>
export CTX_CLUSTER2=<GKE_CONTEXT>

Install Istio in the AWS cluster:

istioctl install \
--context="$CTX_CLUSTER1" \
--set profile=demo -y

Verify the installation:

kubectl get pods -n istio-system \
--context="$CTX_CLUSTER1"

Step 12: Prepare the Application Namespace

Execute:

kubectl label namespace default \
istio-injection=enabled \
--context="$CTX_CLUSTER1"

This enables automatic Envoy sidecar injection for new application pods deployed in the
namespace.

Step 13: Configure the GKE Cluster as a Remote Cluster

The second cluster must be connected to the primary Istio control plane.

Create the Istio namespace:

kubectl create namespace istio-system \
--context="$CTX_CLUSTER2"

For a cross-cloud setup, the clusters normally reside on different networks. Therefore,
students must configure the east-west gateways, expose the Istio control plane and services,
and configure the remote cluster using Istio's primary-remote, different-networks procedure.

Use the official implementation guide:

https://istio.io/latest/docs/setup/install/multicluster/primary-remote_multi-network/

Follow its sequence for:

   1. Setting the network identity of each cluster.
   2.   Configuring the AWS cluster as primary.
   3.   Installing its east-west gateway.
   4.   Exposing the primary control plane.
   5.   Configuring GKE as the remote cluster.
   6.   Installing the remote Istio configuration.
   7.   Installing the remote secret.
   8.   Installing the GKE east-west gateway.
   9.   Exposing services across both clusters.

Important: Do not skip the east-west gateway and network configuration. Merely installing
Istio on two independent clusters does not establish cross-cloud service communication.

Step 14: Verify the Istio Installation

Execute:

kubectl get pods -n istio-system \
--context="$CTX_CLUSTER1"

And:

kubectl get pods -n istio-system \
--context="$CTX_CLUSTER2"

Check the Istio proxy status:

--context="$CTX_CLUSTER1"

Expected Result: The Istio control plane, gateway components and applicable Envoy proxies

PART A: Implement Mutual TLS (mTLS)
Step 1: Understand the Purpose of mTLS

Mutual TLS allows both communicating services to authenticate each other and encrypt their
communication.

In this activity, students will configure Istio to enforce encrypted service-to-service
communication.

Step 2: Create the PeerAuthentication Configuration

Create a new file named:

peer-authentication.yaml

Add the following configuration:

apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: default
spec:
  mtls:
    mode: STRICT

Save the file.

Step 3: Apply the mTLS Configuration

Execute:

kubectl apply -f peer-authentication.yaml \
--context="$CTX_CLUSTER1"

For the remote cluster, apply the corresponding policy as well:

kubectl apply -f peer-authentication.yaml \
--context="$CTX_CLUSTER2"

Step 4: Verify the mTLS Policy

Execute:

kubectl get peerauthentication \
--context="$CTX_CLUSTER1"

Then:

kubectl describe peerauthentication default \
--context="$CTX_CLUSTER1"

Repeat the verification for the remote cluster.

Expected Result: The PeerAuthentication policy should show STRICT as the configured
mTLS mode.

Note: All participating workloads must have compatible Istio proxy injection and certificate
configuration for strict mTLS communication to work.

PART B: Configure Traffic Management and Routing
Step 5: Understand Traffic Routing

Istio allows administrators to control how requests are distributed between different versions
of a microservice.

For this activity, students will configure traffic distribution between two versions of the
Bookinfo Reviews service.

The traffic distribution will be:

       Reviews Version 1: 80%
       Reviews Version 2: 20%

Step 6: Create a DestinationRule

Create a file named:

reviews-destination-rule.yaml

Add:

apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
This configuration identifies the two versions of the Reviews service.

Step 7: Apply the DestinationRule

Execute:

kubectl apply -f reviews-destination-rule.yaml \
--context="$CTX_CLUSTER1"

Step 8: Create a VirtualService

Create another file named:

reviews-virtual-service.yaml

Add:

apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
  - reviews
  http:
  - route:
    - destination:
         host: reviews
         subset: v1
      weight: 80
    - destination:
         host: reviews
         subset: v2
      weight: 20

Step 9: Apply the VirtualService

Execute:

kubectl apply -f reviews-virtual-service.yaml \
--context="$CTX_CLUSTER1"

Step 10: Verify the Traffic Rules

Execute:

kubectl get virtualservice \
--context="$CTX_CLUSTER1"

And:

kubectl get destinationrule \
--context="$CTX_CLUSTER1"
Check the configuration:

kubectl describe virtualservice reviews \
--context="$CTX_CLUSTER1"

Expected Result: Istio should have the routing rules configured to distribute traffic between
Reviews v1 and v2 at an 80:20 weight.

The Bookinfo sample must contain the corresponding versioned workloads and labels for this
routing configuration to work.

Step 17: Generate Application Traffic

collect traffic information.

address and port.

--context="$CTX_CLUSTER1"

Identify the external address of the Istio ingress gateway.

Set the gateway address:

Generate 100 application requests:

for i in $(seq 1 100); do
  curl -s -o /dev/null \

Replace the gateway address and port with the actual values obtained from your cluster.

Step 23: Perform a Resilience Test

The objective is to understand what happens when one cluster or service becomes
unavailable.

For a controlled test:

   1.   Record the normal application response.
   2.   Identify the service or workload being tested.
   3.   Scale down a selected test deployment rather than deleting an entire cloud cluster.
   4.   Send requests again.
   5.   Observe the response.
   6.   Check Kiali and Grafana for changes in service traffic and health.

Example command for scaling down a selected test deployment:

kubectl scale deployment <DEPLOYMENT_NAME> \
--replicas=0 \
--context="$CTX_CLUSTER2"

Restore the deployment after testing:

kubectl scale deployment <DEPLOYMENT_NAME> \
--replicas=1 \
--context="$CTX_CLUSTER2"

Use this test only after confirming that the selected deployment is part of the test
environment.

Important: Traffic failover is not automatic merely because two clusters are connected. It
requires suitable routing, healthy endpoints, gateway configuration, and failover policies.
Students should record whether failover actually occurs in their implementation.
